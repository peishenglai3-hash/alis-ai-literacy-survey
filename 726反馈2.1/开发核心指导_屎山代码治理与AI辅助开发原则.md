## 📋 文档定位与使用说明

### 这份文档是什么

这份文档是本项目的**开发核心指导原则**。它不是某个版本（v3.2/v3.3/v4）的具体设计文档，而是**贯穿所有版本的底层思维框架**——解释"为什么我们的代码会变成屎山"、"屎山对我们有什么影响"、"怎么治本而不只是治标"。

### 为什么需要这份文档

2026-07-26，开发者在执行完726反馈后，反馈了一个深刻的观察：

> "一个bug是bug，一堆bug能work。很多冗杂的功能不是写得差，而是为了适配某个环节、完善整体呈现而搭配的。AI辅助开发（vibe coding）的产出既是黑箱的，也是反黑箱的……随着项目进展，这种强逻辑会越来越加强。"

这个观察揭示了一个**结构性问题**：我们的多轮迭代模式 + AI辅助开发的特性，正在让代码库累积"层叠补丁"。如果不理解这个机制并采取对策，**每一轮反馈都会让代码更难维护，最终拖垮产品迭代速度**。

### 与其他文档的关系

| 文档 | 性质 | 回答的问题 |
|------|------|----------|
| **本文档**（核心指导） | 跨版本的底层思维 | **为什么**会形成屎山 + **长期**怎么治 |
| `v3_726/产品整体反思_从模块化到空间化_v3.3设计升级.md` 第十二章 | v3.3的具体实现策略 | v3.3**这次**怎么改才能不加重屎山 |
| 各版本的议程文档 | 版本具体功能反馈 | **改什么** |

**使用方式**：每轮新迭代开始前，产品方和开发者都应该重读本文档，确认新一轮反馈不会加重屎山。

## 第一部分：问题诊断——什么是"屎山代码"

### 1.1 字面定义

"屎山代码"（shit-mountain code / spaghetti code）是指**经过多轮修改、补丁叠加补丁、各部分互相纠缠、难以单独修改**的代码库。

### 1.2 关键认知：屎山不是"写得很差"

这是最重要的一点。**屎山代码的每一行，单独看可能都没问题**——它们都是为了解决某个具体问题、适配某个具体功能而写的。问题出在**累积方式**上。

#### 装修类比

想象一栋老房子，经历了多任房主：

1. 第一任房主在墙上打了个洞，装了根电线（为了给某个房间供电）
2. 第二任房主为了遮住那根电线，装了个柜子（为了美观）
3. 第三任房主觉得柜子丑，贴了墙纸（为了更好看）
4. 第四任房主想拆掉柜子——但拆了就露出电线
5. 电线也得拆——但电线连着某个房间的灯
6. 灯拆了——那个房间就黑了

**每一任房主的改动都"合理"。但累积起来，这栋房子变成了任何改动都牵一发动全身的"屎山"。**

代码也一样：每一轮反馈的修改都"合理"，但累积起来就是纠缠。

### 1.3 核心法则："一个bug是bug，一堆bug能work"

这是开发者引用的经典说法，含义深刻：

| 情况 | 行为 | 结果 |
|------|------|------|
| **代码里有1个bug** | 这个bug孤立存在，明显是错的 | 系统报错，必须修 |
| **代码里有100个互相补偿的bug** | 每个bug都"补偿"了其他bug的缺陷 | 系统反而能正常运行 |

**为什么一堆bug反而能work？**

因为当一个补丁引发了新问题，开发者（或AI）会再打一个补丁来"修复"这个新问题。层层累加后，所有补丁互相补偿，系统在一种**脆弱的平衡**中运行。

**后果**：
- 删掉任何一个补丁，平衡被打破，系统崩溃
- 这就是为什么"能用的旧代码"常常被保留——它丑，但它work
- 这也是为什么"清理代码"往往是高风险操作

## 第二部分：AI辅助开发为什么会加重屎山

### 2.1 传统编程 vs AI辅助编程

| 维度 | 传统编程 | AI辅助编程（vibe coding） |
|------|---------|------------------------|
| **谁写代码** | 人类程序员 | AI工具（Cursor、Copilot等） |
| **理解深度** | 每行代码都有意图 | 部分代码是AI"自洽"生成的 |
| **代码性质** | 白箱（人完全掌控） | 半黑箱（大方向可见，细节不完全可控） |
| **修改方式** | 理解后精准修改 | 给指令，AI生成修改 |

### 2.2 AI的"自洽性"——屎山的加速器

这是AI辅助开发最关键的特性，也是开发者反馈的核心：

> "它'believe'为了达成这种'正当'的效果，它要这么做，而且随着项目的进展，这种强逻辑就会越来越加强。"

**翻译成具体行为**：

当开发者给AI一个指令（比如"把界面改成单栏"），AI会：

1. **扫描现有代码**，理解当前结构
2. **基于现有代码"自洽地"生成新代码**——它会尽量兼容现有结构，而不是推翻重来
3. **生成补丁代码**，叠加在旧代码之上

**为什么AI倾向于"兼容"而不是"推翻"？**

因为AI的训练数据里，大部分代码都是**增量修改**的（GitHub上的commit历史、Stack Overflow的回答，都是"在现有基础上改"）。AI学到的模式就是"看到旧代码→生成兼容代码"。

### 2.3 多轮迭代 = 洋葱式补丁

把AI的"自洽性"放到我们的多轮迭代中：

```
v1_722（原始代码）
  ↓ AI基于v1生成v2：兼容v1的补丁层
v2_723
  ↓ AI基于v2生成v3：兼容v2（间接兼容v1）的补丁层
v3_725
  ↓ AI基于v3生成v3_726：兼容v3（间接兼容v2、v1）的补丁层
v3_726
  ↓ 现在要生成v3.3：会继续兼容v3_726的补丁层
v3.3
```

**每一层补丁都依赖上一层。** 想剥任何一层，下面露出的都是"缠绕在一起的线"。

这就是为什么开发者在执行726反馈（删除冗杂功能）后说：**"后面再改动可能不大方便"**——他删掉了一层补丁，但依赖这层补丁的其他代码现在悬空了（占位符问题）。

### 2.4 AI辅助开发的"权力关系"

开发者用了一个很精准的词："权力关系"。意思是：

| 传统开发 | AI辅助开发 |
|---------|----------|
| 人类完全掌控代码 | 人类和AI**共同**产出代码 |
| 人类理解每一行 | 人类理解大方向，AI理解细节 |
| 人类可以精准重构 | 人类只能给指令，AI决定具体实现 |
| 重构风险可控 | 重构风险部分不可控（AI可能"自洽地"生成意外代码） |

**这不是说AI辅助开发不好**——它大幅提升了开发速度，让这个产品能在10天内做出MVP。但它有**特定的代价**：代码的累积方式从"人类可控的增量"变成了"AI自洽的补丁层"。

认识到这个代价，才能对症下药。

## 第三部分：这个问题对我们项目的具体影响

### 3.1 我们的迭代历史正是这个问题的放大器

| 版本 | 主要改动 | 累积的补丁层 |
|------|---------|------------|
| v1_722 | 最初原型 | 第1层（基础） |
| v2_723 | 第一次反馈 | 第2层（适配v1的补丁） |
| v2_724 | 第二次反馈 | 第3层（适配v2的补丁） |
| v3_725 | 产品定位重构（四思考窗口+认知地图） | 第4层（大补丁，但没删旧的） |
| v3_726 | 界面简化+四窗口Schema | 第5层（开始删旧补丁，但留下占位符） |
| v3.3 | 认知地图布局+思维气泡 | 第6层（正在规划） |

**每一轮，AI都基于上一轮的代码"自洽地"生成新代码。** 到v3.3时，代码已经是6层洋葱。

### 3.2 具体影响是什么

| 影响层面 | 具体表现 | 严重度 | 说明 |
|---------|---------|-------|------|
| **占位符残留** | 删了组件，但API还在返回`follow_ups`字段、CSS里还有`.follow-up-suggestions`类 | 🟡 低 | 不影响功能，但是"死代码"，累积后影响可读性 |
| **数据结构纠缠** | 四思考窗口的数据可能和旧的"三步流程"数据共用某个state | 🟠 中 | 改一处可能意外破坏另一处 |
| **CSS依赖链** | 某个布局类可能被多个组件共用 | 🔴 高 | 改认知地图布局，可能意外影响结果页 |
| **AI的"自洽性"加强** | 开发者再让AI改代码时，AI会基于"现有屎山"继续打补丁 | 🔴 高 | 越往后越难治，是结构性问题 |
| **迭代速度递减** | 每轮反馈的实现时间越来越长 | 🔴 高 | 补丁层越厚，每轮改动牵连越多 |

### 3.3 对我们有实际影响吗？

**有，但可控。** 具体来说：

1. **v3.3的认知地图布局**可能因为CSS/组件纠缠而比预估工时多0.5-1天
2. **思维气泡系统**是新功能，不依赖旧代码，所以不受影响（前提：按v3.3第十二章策略，独立开发）
3. **未来的迭代**会越来越慢，因为每轮都在"屎山"上加盖新楼层——这是最需要警惕的

**但好消息是**：我们的产品还没上线，还有机会"治本"。

## 第四部分：应对策略——5条治本之策

基于以上诊断，以下是5条**跨版本的应对策略**。这些策略不只适用于v3.3，而是**每一轮迭代都应该遵循的原则**。

### 策略1：减少迭代轮次，增加单轮深度（治本）

**问题**：我们现在每轮反馈都比较"碎"——今天改界面，明天改内容，后天改布局。每轮都是补丁。

**改进**：以后尽量**一次性想清楚**再给开发者。像v3.3这种"整体反思"应该**提前到开发开始前**，而不是在多轮补丁之后再做。

**具体做法**：
- 每一轮新迭代（v4、v5……）开始前，**先做一次"全盘设计review"**
- 把所有界面/数据/交互一次想透，再交付
- 避免"想到一点改一点"的碎片化反馈
- 宁可一轮反馈多花时间想清楚，也不要多轮反馈反复打补丁

**衡量标准**：如果某一轮反馈是在"修改上一轮的修改"，说明在打补丁——应该停下来做整体review。

### 策略2：定点重写而非打补丁（治本）

**问题**：开发者一直在"修改现有代码"，每次都是叠补丁。

**改进**：对**纠缠最严重的模块**，让开发者**推倒重写**，而不是在屎山上修。

**具体做法**：
- 识别"纠缠严重的模块"（通常是改动最频繁、bug最多的模块）
- 对这些模块，**新建独立组件**，从零开始写
- 新组件写好后，**一次性替换**掉旧组件
- 旧组件标记为DEPRECATED，暂时保留（作为fallback）

**衡量标准**：如果某个模块已经经历了3轮以上修改，下一次修改应该考虑重写而非打补丁。

**v3.3的具体应用**：详见`v3.3设计升级文档`第十二章"实现策略"，已对认知地图布局、思维气泡系统等给出了新建组件的具体指导。

### 策略3：给AI完整的"设计意图"（缓解）

**问题**：开发者用AI写代码时，如果只告诉AI"改成单栏"，AI会基于现有代码自洽地打补丁。

**改进**：给AI**完整的设计文档**（像v3.3这种），让它理解"为什么要这么改"，而不只是"改成什么"。AI理解了设计意图，会更倾向于生成**独立的新代码**而不是**兼容旧代码的补丁**。

**具体做法**：
- 每轮反馈文档都保持"设计哲学 + 具体实现"的完整度（v3.3做得不错，有"从模块化到空间化"的设计哲学论述）
- 开发者用AI工具时，**把完整文档喂给AI**，不要只给碎片指令
- 明确告诉AI"不要改旧组件""要新建独立模块"
- v3.3第十二章12.5节有具体的"AI提示正确示范 vs 错误示范"

**衡量标准**：给AI的提示如果少于500字，大概率会导致补丁式产出。

### 策略4：接受一定程度的屎山，专注用户体验（务实）

**问题**：追求"代码干净"是无穷尽的，会拖慢产品交付。

**改进**：**只要用户看到的体验是干净的，底层代码的屎山可以接受**。代码是开发者的成本，体验才是产品方的产出。

**具体做法**：
- v3.3做完后，如果产品能跑通、体验好，就**先上线做访谈**
- 不要为了代码洁癖延误研究进度
- 屎山问题等v4或v5有空闲时再回头治
- 优先保证**用户可见的体验**质量，而非**代码不可见的结构**质量

**衡量标准**：如果"清理代码"的工时超过"做新功能"的工时，说明优先级错了。

**例外情况**：如果屎山已经导致**频繁出bug**或**迭代速度严重下降**，则需要治本（回到策略2）。

### 策略5（最根本）：记录"设计决策的为什么"（预防）

**问题**：屎山的形成，部分是因为**每轮反馈只记录了"改什么"，没记录"为什么改"**。下一轮的AI/开发者看到旧代码时，不知道某个写法是有意为之还是历史遗留。

**改进**：每轮反馈文档都要记录**设计决策的理由**，而不只是改动内容。

**具体做法**：
- v3.3文档其实已经开始做这件事了（有"设计哲学层面"的决策记录、有三轮界面演化复盘）
- 以后每轮反馈都保持这种深度
- 对关键决策，记录"为什么这么做"和"为什么不那么做"（被否决的方案）
- 在代码层面，对非显而易见的写法，加注释说明"为什么这么写"

**衡量标准**：6个月后回头看某段代码，如果无法判断"这是有意为之还是历史遗留"，说明文档不够。

## 第七部分：常见误区与纠正

### 误区1："屎山代码 = 烂代码"

**纠正**：屎山不是烂代码。屎山的每一行都"合理"，问题是累积方式。不要责怪开发者（或AI），要理解屎山是多轮迭代 + AI辅助开发的**结构性后果**。

### 误区2："只要清理干净就好了"

**纠正**：清理屎山是高风险操作。"一堆bug能work"——清理掉某些"看起来冗余"的代码，可能打破补丁之间的脆弱平衡，导致系统崩溃。清理必须**有测试覆盖**且**逐步进行**。

### 误区3："AI能帮我自动重构"

**纠正**：不能。AI的重构能力有限，特别是对纠缠严重的代码。AI更擅长**基于现有代码生成兼容代码**（打补丁），而不是**理解整个架构后做精准重构**。重构需要人类主导，AI只能辅助。

### 误区4："v3.3按策略做完后，屎山就解决了"

**纠正**：v3.3第十二章的策略只能**避免加重屎山**，不能消除已有的屎山。已有的补丁层仍然存在。要真正"治本"，需要长期坚持5条原则，并在合适的时机做整体重写。

### 误区5："产品没上线就追求代码完美"

**纠正**：产品没上线时，最优先的是**验证产品设计是否正确**。如果为了代码洁癖延误了访谈验证，是本末倒置。屎山可以容忍，但不能无限增长——掌握平衡。
