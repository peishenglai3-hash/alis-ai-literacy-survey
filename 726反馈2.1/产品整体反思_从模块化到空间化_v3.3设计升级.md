## 一、核心设计哲学：从"模块化"到"空间化"

### 1.1 当前的问题本质

用户（产品方）明确指出：

> "界面过于模块化，且界面呈从上到下的分布，属于手机端的界面逻辑，并不符合网页端的体验。"

这个观察非常精准。问题的本质不是"信息多少"，而是**信息组织方式错了**。

### 1.2 两种界面思维的根本差异

#### 模块化思维（手机端逻辑）

```
模块1 → 模块2 → 模块3 → 模块4 → 模块5
（纵向滚动，平等堆叠）
```

**隐含假设**：所有信息重要性相同，用户按顺序滚动消费。

**适用场景**：手机端（屏幕窄，只能纵向）、信息流消费（朋友圈、抖音）。

**失败场景**：访谈实时场景（访谈者正在听对方说话，没有时间滚动查找）。

#### 空间化思维（网页端逻辑）

```
┌──────────────┬───────────┐
│              │           │
│   焦点区      │  周边觉察区│
│  （中央）     │  （右侧）  │
│              │           │
├──────────────┴───────────┤
│      深度钻取区（下方）     │
└──────────────────────────┘
```

**隐含假设**：信息有不同的重要性层次，应该分配到不同的空间角色。

**三种空间角色**：

| 空间角色 | 承担的内容 | 视觉权重 | 交互模式 |
|---------|----------|---------|---------|
| **焦点区（中央）** | "必须看"的内容 | 高 | 持续注视 |
| **周边觉察区（右侧）** | "可能想到"的内容 | 低-中 | 余光扫描，按需注视 |
| **深度钻取区（下方/展开）** | "想要深挖"的内容 | 默认隐藏 | 主动展开 |

**适用场景**：网页端（屏幕宽，可用2D空间）、专业工具（IDE、设计软件、研究工具）。

### 1.3 为什么访谈场景必须是"空间化"

访谈是一个**实时的、高认知负荷的、需要多视角同时在线**的任务：

- 访谈者正在倾听对方说话（占用主注意力）
- 同时需要保持研究框架（周边觉察：这道题在测什么维度）
- 同时可能产生瞬时灵感（周边觉察：这个回答可能关联Q5）
- 需要时想查阅深度信息（按需钻取：素养关联的具体链条）

**只有空间化布局能同时支持这三种需求**。单栏纵向布局会迫使访谈者在"听对方"和"滚动查找信息"之间切换——这是反访谈的。

## 二、三轮界面演化复盘

### 2.1 第一轮：v3_725 的"认知地图"原型（设计智慧最高）

```
┌──────────────────────────┬──────────────┐
│                          │              │
│   中央极简区              │  右侧思维气泡 │
│   （焦点）                │  （周边觉察） │
│   - Q1 题目              │  💭 想想(3)   │
│   - 答案选择器            │  ⏱14:28 ... │
│                          │  ⏱14:25 ... │
│                          │  [+ 添加]    │
│                          │              │
├──────────────────────────┴──────────────┤
│   下方三模块（深度钻取）                  │
│   故事入口 / 选择解释 / 研究关联          │
└─────────────────────────────────────────┘
```

**评价**：✅ 这是网页原生的空间隐喻——像研究者的书桌。中央是主笔记，右侧是便签纸，下方是参考资料。设计智慧最高。

### 2.2 第二轮：v3.1 实际实现（三栏等权，信息过载）

```
┌──────────┬──────────────────┬──────────┐
│ 左栏     │ 中栏（塞满）      │ 右栏     │
│ 旅程地图 │ 题目+答案         │ 用户类型 │
│ 15题列表 │ +过渡参考         │ 装饰性   │
│          │ +追问建议(5条)    │ 元数据   │
│          │ +思考窗口         │          │
│          │ +访谈记录框       │          │
└──────────┴──────────────────┴──────────┘
```

**偏离点**：把"认知地图"误解成了"三栏等权内容区"。三栏都变成了"重要内容"，失去了"中央焦点+周边觉察+按需深度"的层次结构。

### 2.3 第三轮：v3.2（726反馈）的"单栏极简"（过度修正）

```
┌─────────────────────────┐
│ 进度条                   │
│ 题目                     │
│ 答案选择器               │
│ [题目理解][经验][选择][素养]│
│ 思考窗口内容             │
│ 导航按钮                 │
└─────────────────────────┘
max-width: 800px
flex-direction: column
```

**偏离点**：
- ❌ 抛弃了 v3_725 的空间智慧（中央/周边/深度的层次）
- ❌ 把网页降维成手机（单栏纵向滚动）
- ❌ 思维气泡被降级为"可选悬浮组件，默认不显示"
- ❌ 屏幕右半边的"周边觉察空间"完全浪费成留白

**坦白说**：726反馈（我协助生成的）在"清理过载"上是对的，但在"替代布局"上选错了方向。它用"减法思维"解决了"加法错误"，但没能回到原本的"空间思维"。

### 2.4 第四轮：v3.3（本文档）的"认知地图极简"

不是回到 v3.1 的三栏过载，而是**回到 v3_725 原本的空间智慧**，再叠加思维气泡这个旗舰特性：

```
┌────────────────────────┬─────────────────┐
│                        │                 │
│  【中央焦点区】          │ 【右侧觉察带】   │
```

## 三、现有引擎的优势（必须保留）

虽然布局有问题，但以下几样东西是**对的**，不应在后续迭代中丢失：

### 3.1 数据驱动的 Question Schema 思路

每道题都有独立的关键词、素养关联、故事入口、跨题关联——这是**正确的底层数据架构**。界面的混乱不是数据的错，是渲染层的错。

**保护措施**：726反馈的议程3（15题完整Schema）照常执行，不动。

### 3.2 四思考窗口的内容架构

"题目理解 / 经验叙事 / 选择解释 / 素养关联"这四个维度本身设计得很好——它们对应了质性访谈的四种认知视角（释义/回忆/反思/理论化）。

**问题在呈现方式**（tab堆叠），不在内容。本文档第六章会重新设计呈现方式。

### 3.3 "去价值化"的内容原则

"每种回答都值得理解，不暗示正确答案"——这是产品最重要的研究伦理底线。引擎至今没有滑向"AI告诉你该问什么"，这点很关键。

**保护措施**：思维气泡的所有AI生成内容，必须经过"去价值化"过滤（见第八章）。

### 3.4 离线生成+人工审核的内容流程

不让AI实时生成访谈内容，而是预先结构化——这是正确的质量控制。

**保护措施**：思维气泡的"预设气泡"和"规则触发气泡"离线生成，只有"语义分析气泡"可实时生成（且需明确标注"AI推测"）。

## 四、现有引擎的深层劣势

### 4.1 劣势1：模块化抹杀重要性差异

现在的设计把所有信息切成平等模块纵向堆叠。但访谈中，"题目"和"思考气泡"的重要性根本不对等——题目是焦点，气泡是周边。把它们都塞进单栏纵向流，就是在抹杀这种重要性差异。

### 4.2 劣势2：滚动检索成本高

现在的单栏设计，访谈者要看到"素养关联"窗口，必须滚动到底部。但访谈是**实时进行**的——访谈者没有时间滚动查找，他正在听对方说话。

v3_725 的"认知地图"设计是**一屏可达**的：眼睛扫一下右侧就能看到气泡，扫一下下方就能看到深度模块。这种"空间记忆"（spatial memory）是网页相对手机的独有优势，被单栏设计完全抹掉了。

### 4.3 劣势3：思维气泡的潜力被严重低估

在 v3_725 里设计的思维气泡，被726反馈降级为"可选悬浮组件，60%透明度，默认不显示"。这是**重大损失**。

思维气泡的真正价值不是"显示预设问题"，而是：
- 捕捉访谈中的"潜在情况"（受访者情绪 + 访谈者灵感）
- 提供"交互入口"（点击气泡→展开为深度笔记→可能触发跨题关联）
- 记录访谈者的瞬时灵感（按回车快速记录，不打断倾听）

它是一个**"轻量级、低侵入、高觉察"**的组件——这种设计在访谈辅助工具里几乎是独创的。把它弱化，等于丢掉了产品最有辨识度的设计语言。

### 4.4 劣势4：进度条是"线性"的，但访谈是"空间"的

顶部进度条 "阶段1: 认识AI | Q1/2 ▓▓░░░" 隐含的隐喻是：访谈是一条**直线**，从A走到B。

但实际上15题分布在6个阶段里，访谈者需要在"现在到哪了""还有多远""能不能回去看Q3"之间建立**空间感**。线性进度条给不了这种空间感——它只能告诉你"走了多远"，但不能告诉你"你在地图上的什么位置"。

### 4.5 劣势5：访谈前/中/后的状态没有区分

现在的界面是"一种布局打天下"——不管访谈者是在准备、访谈中、还是回顾，界面都长一样。但这是三种**完全不同的认知任务**：

| 状态 | 任务 | 信息密度需求 |
|------|------|------------|
| 访谈前 | 完整briefing，熟悉所有题 | 高 |
| 访谈中 | 实时倾听，焦点+周边觉察 | 低-中 |
| 访谈后 | 回看15题，发现跨题模式 | 高（地图式）|

### 6.2 三区结构说明

#### 中央焦点区（承担"必须看"）

**包含**：
- 阶段标识 + 题号（"阶段1: 认识AI | Q1/2"）
- 题目内容
- 关键词行
- 答案选择器（1-7）
- 被访者回答快速输入框（**不是大段文本框，是关键词式快速记录**）
- 导航按钮

**视觉权重**：最高。背景白，文字深色，字体最大。

**交互**：持续注视区域，不需要主动展开。

#### 右侧觉察带（承担"可能想到"）

**包含**：
- 思维气泡列表（带时间戳）
- 添加想法入口

**视觉权重**：低-中。默认60%透明度，鼠标悬停时80%。

**交互**：余光扫描区域。点击气泡可展开为深度笔记（见方向2）。

#### 下方钻取区（承担"想要深挖"）

**包含**：
- 四个tab：题目理解 / 经验叙事 / 选择解释 / 素养关联
- 同一时间只展开一个tab
- 展开后显示对应内容

**视觉权重**：默认隐藏（折叠状态）。展开时浮现。

**交互**：主动展开区域。访谈者按需查阅，不强制阅读。

## 七、方向2详细设计：思维气泡系统（旗舰特性）

### 7.1 设计理念

思维气泡是产品的**核心差异化特性**。它的设计哲学是：

> **不替代人类思考，但捕捉访谈中的"潜在情况"，提供一个轻量级的交互入口。**

"潜在情况"分两类（已与产品方确认）：

| 类型 | 关注对象 | 来源 |
|------|---------|------|
| **A：受访者的潜在情绪/态度** | 对方在回答时露出的题面之下信号 | AI语义分析、一致性检测、关键词分析 |
| **B：访谈者的潜在灵感** | 访谈者此刻应该想到什么 | Schema预设、跨题关联规则、访谈者手动添加 |

### 7.2 两类"潜在情况"的详细设计

#### 类型A：受访者的潜在情绪/态度（觉察对方）

**目的**：帮助访谈者捕捉受访者**回答文本之下**的信号。

**触发逻辑**：

| 检测维度 | 示例触发条件 | 气泡内容示例 |
|---------|------------|------------|
| **答案-回答一致性** | 选7分但回答里有"应该算是""大概" | "高分但语气不坚决？可能在表现自信但实际边界模糊" |
| **关键词重复** | 反复提到"方便""好用" | "强调实用性，是否把'判断AI'等同于'好用'？" |
| **回避检测** | 描述时回避具体例子 | "回避了具体案例，判断依据可能停留在抽象层面" |
| **情绪标记** | 描述具体经历时用词变得兴奋/负面 | "这段经历触发了情绪，值得深挖故事入口" |
| **概念混淆** | 把"AI推荐"说成"AI生成" | "AI概念可能停留在功能层，可在Q14（AI观变化）追问" |

**实现方式**：
- **MVP版本**：基于关键词的规则匹配（成本最低）
  ```python
  def detect_hedging(answer_score, response_text):
      hedging_words = ["应该", "大概", "可能", "算是", "差不多"]
      if answer_score >= 6 and any(w in response_text for w in hedging_words):
          return {
              "type": "interviewee_signal",
              "content": "高分但语气不坚决？可能在表现自信但实际边界模糊",
              "confidence": "medium"
          }
      return None
  ```
- **进阶版本**：调用LLM做语义分析（成本中，需审核Prompt）

#### 类型B：访谈者的潜在灵感（觉察自己）

**目的**：帮助访谈者保持研究视角，捕捉跨题关联和瞬时灵感。

**三个子来源**：

**B1：Schema预设气泡**（来自Question Schema）

每道题的Schema里预设了2-3个"访谈者应思考的问题"，题目加载时显示。

```json
{
  "Q1": {
    "思维气泡预设": [
      "这个人如何理解'AI'？",
      "他的判断依据是什么？",
      "他有没有经历过误判？"
    ]
  }
}
```

**B2：跨题关联气泡**（基于规则触发）

当受访者的回答命中某关键词时，触发跨题关联提醒。

```python
# 规则示例
CROSS_QUESTION_RULES = [
    {
        "trigger_keywords": ["ChatGPT", "用AI", "写代码", "工具"],
        "target_question": "Q3",
        "bubble_content": "提到具体工具使用 → 可能关联Q3（使用习惯）"
    },
    {
        "trigger_keywords": ["一开始以为", "以前觉得", "变化"],
        "target_question": "Q14",
        "bubble_content": "概念有变化信号 → 关联Q14（AI观变化）"
    }
]

def check_cross_question(response_text):
    triggered = []
    for rule in CROSS_QUESTION_RULES:
        if any(kw in response_text for kw in rule["trigger_keywords"]):
            triggered.append({
                "type": "cross_question",
                "content": rule["bubble_content"],
                "target_question": rule["target_question"]
            })
    return triggered
```

**B3：访谈者手动添加**（自记录灵感）

访谈者在倾听过程中产生的瞬时想法，按回车快速记录。

```jsx
// 快速添加气泡
<input
  placeholder="+ 添加想法（按回车发送）"
  onKeyDown={(e) => {
    if (e.key === 'Enter' && e.target.value.trim()) {
      addBubble({
        type: 'interviewer_note',
        content: e.target.value.trim(),
        timestamp: Date.now()
      });
      e.target.value = '';
    }
  }}
/>
```

### 7.3 气泡的数据结构

```typescript
interface ThoughtBubble {
  bubble_id: string;           // 唯一ID
  timestamp: number;           // 时间戳（毫秒）
  question_id: string;         // 关联的题号（如"Q1"）

  source: 'schema_preset'      // 来源：Schema预设
       | 'cross_question'      // 来源：跨题关联规则
       | 'interviewer_note'    // 来源：访谈者手动添加
       | 'interviewee_signal'  // 来源：受访者语义信号（AI）
       | 'semantic_match';     // 来源：语义匹配（AI）

  category: 'interviewee'      // 类型A：觉察对方
          | 'interviewer';     // 类型B：觉察自己

  content: string;             // 气泡内容（简短一句话）

  // 可选字段
  target_question?: string;    // 跨题关联的目标题号
  confidence?: 'high' | 'medium' | 'low';  // AI推测的置信度
  pinned?: boolean;            // 是否被钉住（跨题保留）

  // 状态
  status: 'pending'            // 待处理
       | 'expanded'            // 已展开为深度笔记
       | 'dismissed';          // 已忽略
}
```

### 7.6 "去价值化"过滤（关键伦理设计）

**所有AI生成的气泡（类型A和类型B的AI部分）必须经过去价值化过滤**：

❌ **禁止**的表述（暗示正确答案或价值判断）：
- "他应该这样回答才对"
- "这个回答说明他AI素养不足"
- "建议你引导他改变看法"

✅ **允许**的表述（开放性、描述性、探索性）：
- "这段经历似乎触发了情绪，值得深挖"
- "强调实用性，是否把'判断AI'等同于'好用'？"
- "回避了具体案例，判断依据可能停留在抽象层面"

**过滤规则**（实现层面）：

```python
def filter_bias(content):
    """过滤AI生成气泡的价值判断"""
    forbidden_patterns = [
        "应该", "必须", "正确", "错误", "不足", "不够",
        "素养低", "能力差", "建议你引导", "需要纠正"
    ]
    for pattern in forbidden_patterns:
        if pattern in content:
            return None  # 拒绝生成
    return content
```

## 十、风险与应对

### 风险1：认知地图布局在开发者端实现复杂度

**风险描述**：开发者可能习惯了单栏布局，对grid布局不熟悉。

**应对**：
- 提供完整的CSS代码（第六章已给）
- 提供ASCII布局图作为视觉参考
- 设置验收标准："一屏可见焦点区+觉察带，无需滚动"

### 风险2：思维气泡的AI生成内容质量

**风险描述**：AI生成的气泡可能不准确，甚至误导访谈者。

**应对**：
- MVP版本只做"规则触发"气泡（不调LLM），准确率可控
- AI生成的气泡必须标注"AI推测"标签
- 设置置信度字段，低置信度的不显示
- 所有AI生成内容经过"去价值化"过滤（第七章已给规则）

### 风险3：受访者信号检测的隐私问题

**风险描述**：检测受访者的情绪/态度可能涉及隐私。

**应对**：
- 信号只用于"提醒访谈者注意"，不存储为受访者画像
- 信号基于回答文本的**语言特征**（hedging词、重复词），不做情感判定
- 在访谈后回顾模式中，受访者信号气泡可单独删除

### 风险4：10天工时不够

**风险描述**：上述所有方向加起来可能超过10天。

**应对**：
- P0必须完成（认知地图布局 + 思维气泡MVP版）
- P1可视情况裁剪（受访者信号检测、回顾模式）
- P2可延后（访谈前准备模式）
- 如果实在紧张，**访谈中状态必须完整**，其他可简化

### 🆕 风险5：屎山代码——AI辅助开发的层叠补丁陷阱

**风险描述**：开发者反馈指出，经过多轮迭代（v1→v2→v3_725→v3_726），代码库已积累多层"适配补丁"。AI辅助开发工具（Cursor、Copilot等）每轮都会基于现有代码"自洽地"生成新代码——它看到旧结构，就生成兼容旧结构的新代码，而不是推翻重来。结果是每一层补丁都依赖上一层，形成"洋葱式"纠缠。在旧组件上改v3.3，会继续叠加补丁层，让代码越来越难维护。

**应对**（详见第十二章"实现策略"）：
- **策略1**：v3.3的新功能（认知地图布局、思维气泡）新建独立组件，不在旧组件上改
- **策略2**：删除组件后的占位符（CSS类、API字段）允许暂时保留，加`DEPRECATED`注释，不要为了清理而冒险
- **策略3**：思维气泡系统作为独立模块开发，不依赖现有访谈状态管理
- **策略4**：给AI工具的提示必须包含完整设计文档，禁止只给碎片化指令

## 十二、实现策略：避免屎山代码与占位符清理

> ⚠️ **本章是v3.3能否成功落地的关键。**
> 开发者反馈指出：多轮迭代后代码库已积累"层叠补丁"，在旧组件上改v3.3会继续叠加补丁层。本章提供4条具体策略，指导开发者**怎么改才能不加重屎山**。

### 12.1 问题背景：AI辅助开发的"层叠补丁"陷阱

开发者反馈的核心观察（原文精神）：

> "一个bug是bug，一堆bug能work。很多冗杂的功能不是写得差，而是为了适配某个环节、完善整体呈现而搭配的。AI辅助开发（vibe coding）的产出既是黑箱的，也是反黑箱的——它有规律可循，所以能把框架搭出来；但它的概率机制又意味着产出具有不可控和自洽性，随着项目进展，这种强逻辑会越来越加强。"

**翻译成具体行为**：

每一轮反馈，AI辅助开发工具（Cursor、Copilot等）都会基于现有代码"自洽地"生成新代码：

1. AI看到项目里已有的旧结构（比如旧人格类型逻辑）
2. AI生成新代码时，会**兼容旧结构**而不是推翻重来（因为它"believe"这样才"正当"）
3. 新代码和旧代码形成**互相依赖的补丁层**
4. 下一轮迭代时，AI又基于这个"更厚的洋葱"继续打补丁

**结果**：到v3.3时，代码已经是一颗"洋葱"——v1的原始代码 + v2的适配补丁 + v3_725的适配补丁 + v3_726的适配补丁。你想剥任何一层，下面露出的都是"缠绕在一起的线"。

**v3.3的实施必须打破这个循环**。下面是4条策略。

### 12.2 策略1：新建组件 vs 改旧组件

**核心原则**：v3.3的新功能尽量**新建独立组件**，不在旧组件上打补丁。

| 功能 | ❌ 不要这样做 | ✅ 应该这样做 |
|------|-------------|------------|
| 认知地图布局 | 在旧`InterviewPage.jsx`上改CSS | **新建`CognitiveMapLayout.jsx`**，从零搭建 |
| 思维气泡系统 | 复用旧的"访谈记录"组件逻辑 | **新建`ThoughtBubblePanel.jsx`**，独立状态管理 |
| 三种界面状态 | 在现有路由上硬编码条件分支 | **新建`InterviewStateContext.jsx`**，集中管理 |
| 四思考窗口数据 | 改现有的`questionData.js` | **新建`questionSchemas.js`**（从议程3导入） |

**标准操作流程**：

```
Step 1: 新建组件文件（不引用任何旧组件的内部逻辑）
       ↓
Step 2: 新组件作为独立模块（有自己的CSS、state、数据流）
       ↓
Step 3: 新组件写好并测试通过后，在路由层一次性替换旧组件
       ↓
Step 4: 旧组件不删除，标记为 DEPRECATED（等新组件稳定后再清理）
```

**好处**：
- ✅ 新代码是干净的，不带历史包袱
- ✅ 旧代码仍然可用（作为fallback，出问题可快速回退）
- ✅ AI辅助开发时，新组件没有旧代码"污染"，生成质量更高

### 12.3 策略2：占位符处理原则

**核心原则**：删除组件后残留的"占位符"（CSS类、API字段、state字段）**允许暂时保留**，但必须标记。不要为了"代码干净"而冒险改动正在工作的代码。

#### 什么是"占位符"

执行726反馈的删除清单后，会留下这些残留：

| 残留类型 | 示例 | 是否影响功能 | 处理方式 |
|---------|------|------------|---------|
| **import语句** | `import FollowUpSuggestions from ...` | ❌ **会导致编译错误** | **必须立即删除** |
| **组件引用** | `<FollowUpSuggestions />` | ❌ **会导致编译错误** | **必须立即删除** |
| **CSS类** | `.follow-up-suggestions` | ✅ 不影响 | 加注释保留 |
| **API字段** | `question.follow_ups`（后端还在返回） | ✅ 不影响 | 加注释保留 |
| **state字段** | `interviewRecord`（UI已删，state还在） | ✅ 不影响 | 加注释保留 |
| **工具函数** | `formatFollowUps()`（无人调用） | ✅ 不影响 | 加注释保留 |

#### 标记模板

```javascript
// DEPRECATED v3.3 (2026-07-26)
// 原因：FollowUpSuggestions组件已在v3.726反馈中删除
// 清理时机：v3.3稳定后统一清理（预计MVP结束后1-2周）
// 影响范围：仅此文件，无外部引用
const interviewRecord = useState('');
```

```css
/* DEPRECATED v3.3 (2026-07-26)
 * 原因：FollowUpSuggestions组件已删除
 * 清理时机：v3.3稳定后统一清理
 */
.follow-up-suggestions { ... }
```

#### 三条铁律

1. **会导致编译错误的残留** → 立即删除（如import已删组件）
2. **不影响功能的残留** → 暂时保留，加`DEPRECATED v3.3`注释
3. **清理时机统一安排** → 等v3.3全部稳定后（预计MVP结束后1-2周），做一次集中清理

**禁止行为**：
- ❌ 为了"代码干净"而大规模清理占位符（高风险、低收益、当前不必要）
- ❌ 删除某个占位符时，顺手"优化"周边代码（容易引入隐蔽bug）
- ❌ 在没有测试覆盖的情况下重构纠缠的代码

### 12.4 策略3：模块独立性原则

**核心原则**：v3.3的新功能（特别是思维气泡系统）必须作为**独立模块**开发，不依赖现有的访谈状态管理。

#### 思维气泡系统的独立性要求

| 维度 | ❌ 不要这样做 | ✅ 应该这样做 |
|------|-------------|------------|
| **数据存储** | 把气泡数据塞进现有的`interviewData` | 新建`bubbleStore`（独立context/reducer） |
| **持久化** | 复用现有的访谈保存逻辑 | 新建`bubblePersistence.js`，独立保存到localStorage |
| **事件监听** | 监听现有组件的内部事件 | 通过props或订阅模式获取数据 |
| **CSS样式** | 复用现有的`.interview-*`类名 | 新建`.bubble-*`命名空间，样式独立 |
| **数据结构** | 在现有的`question`对象上加字段 | 新建`ThoughtBubble`接口（第七章已定义） |

#### 推荐的文件结构

```
/src/
  /components/
    CognitiveMapLayout.jsx          ← 新建：认知地图布局
    CognitiveMapLayout.css
    ThoughtBubblePanel.jsx          ← 新建：气泡面板
    ThoughtBubblePanel.css
    FocusZone.jsx                   ← 新建：中央焦点区
    AwarenessZone.jsx               ← 新建：右侧觉察带
    DrillZone.jsx                   ← 新建：下方钻取区
  /store/
    bubbleStore.js                  ← 新建：气泡独立state
    interviewStateContext.js        ← 新建：三种界面状态
  /utils/
    bubblePersistence.js            ← 新建：气泡持久化
    crossQuestionRules.js           ← 新建：跨题关联规则
    hedgingDetector.js              ← 新建：受访者信号检测
  /data/
    questionSchemas.js              ← 新建：15题Schema数据
  /deprecated/
    InterviewPage.jsx               ← 旧组件移至此处（标记DEPRECATED）
    FollowUpSuggestions.jsx         ← 旧组件
    TransitionReference.jsx         ← 旧组件
```

**为什么这很重要**：

如果思维气泡系统和现有访谈逻辑纠缠，未来任何对访谈逻辑的改动都可能破坏气泡功能。保持独立性，意味着：
- 气泡功能可以**独立测试**
- 气泡数据可以**独立迁移**
- 未来重写访谈逻辑时，气泡系统**不需要跟着重写**

### 12.5 策略4：AI辅助开发的提示原则

**核心原则**：开发者使用AI工具（Cursor、Copilot等）实现v3.3时，**必须提供完整的设计文档**，禁止只给碎片化指令。

#### 为什么这很重要

AI工具的"自洽性"会导致它基于现有代码打补丁：

**错误示范**（碎片化指令）：
```
把访谈界面改成grid布局，左边题目，右边气泡，下面思考窗口。
```

AI收到这种指令后，会：
1. 打开现有的`InterviewPage.jsx`
2. 看到现有的`flex-direction: column`
3. "自洽地"生成在现有基础上改成grid的补丁代码
4. 产出结果带着旧逻辑的包袱

**正确示范**（完整设计文档）：
```
请阅读这份v3.3设计升级文档（附上完整文档）。

你需要新建一个 CognitiveMapLayout 组件，
实现文档第六章描述的"中央焦点区 + 右侧觉察带 + 下方钻取区"三区结构。

要求：
- 不要修改现有的 InterviewPage 组件
- 新组件应该是独立的，有自己的CSS和state
- 不要引用现有组件的内部模块
- 参考文档第十二章的实现策略
```

AI收到这种指令后，会：
1. 理解这是一个**新的布局范式**
2. 更倾向于生成**独立的新代码**
3. 产出结果更干净

#### AI提示的4条规则

| 规则 | 说明 |
|------|------|
| **提供完整文档** | 把v3.3文档完整喂给AI，不要只摘要 |
| **说明"不要做什么"** | 明确告诉AI"不要改旧组件""不要引用旧模块" |
| **指定新建文件名** | 告诉AI应该新建哪些文件（如`CognitiveMapLayout.jsx`） |
| **要求独立模块** | 强调新组件要有独立的CSS、state、数据流 |

### 12.6 给开发者的执行检查清单

实现v3.3时，请逐项确认：

- [ ] 认知地图布局是**新建组件**（`CognitiveMapLayout.jsx`），不是改旧组件
- [ ] 思维气泡系统有**独立的state/context**（`bubbleStore.js`），不复用现有访谈state
- [ ] 气泡持久化逻辑**独立编写**（`bubblePersistence.js`），不复用现有保存逻辑
- [ ] 给AI工具的提示包含**完整v3.3设计文档**，不只是碎片指令
- [ ] 删除组件后的CSS类/API字段/state**加上了`DEPRECATED v3.3`注释**
- [ ] 旧组件**没有删除**，标记为DEPRECATED
- [ ] 新建的组件文件**没有import旧组件的内部模块**
- [ ] 路由层是**一次性替换**（`<InterviewPage />` → `<CognitiveMapLayout />`），不是渐进式替换

## 十三、设计反思与未来展望

### 13.1 这次反思的方法论价值

本次反思揭示了一个重要的设计教训：

> **"减法思维"解决不了"加法错误"。当信息过载时，不是简单地"删掉模块"，而是要重新思考"信息应该住在哪里"。**

726反馈用了减法思维（删模块、缩宽度），解决了眼前的过载问题，但没能回到原本的空间智慧。这次反思用"空间思维"重新组织信息，才找回了 v3_725 的设计初心。

### 13.2 产品的长期可能性

思维气泡系统如果做好，**本身就可以成为研究产出**：

- 访谈结束后，气泡的时间戳序列 = 访谈者的"思维心电图"
- 被钉住的气泡 = 研究者认为最有价值的洞察
- 跨题关联气泡 = 自发发现的理论链路
- 多次访谈的气泡聚合 = 群体层面的洞察模式

这意味着产品不仅是"访谈辅助工具"，还可能是**"访谈研究的方法学创新"**——用气泡数据反推研究者的认知过程，这是质性研究方法学里的新方向。

   - 选项C：默认隐藏，访谈者主动展开（最简洁，但可能忘记看）
